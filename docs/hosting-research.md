# Hosting Mistracker for a free pilot

Provider terms checked November 9, 2026.

## Recommended setup

Use **Render Static Sites for the interface and Supabase Free for Google sign-in, Postgres, and private screenshot storage**. Render provides an HTTPS `onrender.com` address. Add a separate hosted build that reuses Mistracker’s HTML, CSS, and browser JavaScript. The [current demo build](../build_demo.py) installs an [in-memory API mock](../demo/demo-mode.js), so the hosted build needs a real data adapter. Keep the local Flask/SQLite app and sample demo available. [Render Static Sites](https://render.com/docs/static-sites)

| Service | What the free plan provides | What happens at the limit |
| --- | --- | --- |
| Render | Static site with 5 GB outbound bandwidth and 500 build minutes per month on current Hobby plans | With no payment method, bandwidth overage suspends free services for the rest of the month and exhausting build minutes blocks new builds. [Hobby plan limits](https://render.com/docs/new-workspace-plans#hobby), [Render billing FAQ](https://render.com/docs/faq#all-of-my-services-run-on-free-instances-can-i-still-be-billed) |
| Supabase | 500 MB Postgres per project, 1 GB file storage, 5 GB egress plus 5 GB cached egress, and 50,000 monthly active auth users | Continuing to exceed quotas can restrict service on Free. Low activity over a week can pause the project. The owner can manually resume it in the dashboard within a year. [Pricing](https://supabase.com/pricing), [billing FAQ](https://supabase.com/docs/guides/platform/billing-faq), [pausing](https://supabase.com/docs/guides/platform/free-project-pausing) |

Use the provider URLs and keep both services on their free plans. This is a $0 pilot with usage and availability limits. Supabase Free lacks regular automatic backups, so export the database and storage objects separately. [Supabase backups](https://supabase.com/docs/guides/platform/backups)

Start with Google sign-in using only basic identity scopes. Set the Render origin in Google and Supabase and register Supabase’s project callback with Google. Google’s test-user allowlist has an exception for basic sign-in, so enforce pilot access in the app’s database and storage policies. The default Supabase email service delivers only to project-team addresses, so public magic links, confirmations, and password resets would require a separate SMTP setup. [Supabase Google setup](https://supabase.com/docs/guides/auth/social-sign-in/auth-google), [Google OAuth audience](https://support.google.com/cloud/answer/15549945?hl=en), [Supabase email delivery](https://supabase.com/docs/guides/auth/auth-smtp)

## Rollout

1. Get one workflow working on a separate hosted preview with test data. Sign in, create a mistake, attach a screenshot, and reopen the mistake on a second browser. Give each mistake and its review history an owner. Scope list, search, analytics, category actions, and reviews to that owner with Postgres row-level security. Store screenshots in a private bucket under account-specific paths, with matching policies. Use the browser publishable key with the user session and keep privileged keys out of the build. [Row-level security](https://supabase.com/docs/guides/database/postgres/row-level-security), [storage policies](https://supabase.com/docs/guides/storage/security/access-control)
2. Check isolation from two separate accounts and while signed out. Try direct requests for the other account’s records and screenshot paths, including edits, deletes, reviews, and exports. Bring over the [review workflow](../app/reviews.py) and give users an export of their own mistakes, reviews, and images. Keep the [whole-database restore](../app/backup.py) in the local app.
3. Invite a small group and enforce a screenshot size limit in the bucket, along with a per-account upload quota on the backend. Size the pilot well below the 1 GB storage allowance. A working starting budget is 10 accounts at 25 MB each, with images capped at 1 MB after optional browser-side compression. Review storage and bandwidth before expanding access. [Bucket limits and access controls](https://supabase.com/docs/guides/storage/buckets/fundamentals)

## Other options

- **Deploy Flask to a free Render web service.** The app’s current SQLite file and uploaded images would disappear on restart, redeploy, or idle spin-down. Free Render Postgres expires after 30 days. Using an external data service would still require changes and would add a Flask service with a cold start. [Render free hosting](https://render.com/docs/free)
- **Cloudflare Workers, D1, and KV.** Python Workers support Flask, but persistence needs D1 or another managed data adapter, plus separate auth. D1 Free has a 500 MB per-database limit and 2 MB per row or blob. KV Free can store images with a 1 GB account limit and 1,000 writes per day, with eventual consistency. Free Workers have 100,000 requests/day and 10 ms of CPU time per request. R2 requires a separate subscription and charges above its included usage, making it a poor fit for this pilot’s no-bill constraint. [Flask on Workers](https://developers.cloudflare.com/workers/languages/python/packages/flask/), [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [KV limits](https://developers.cloudflare.com/kv/platform/limits/), [KV consistency](https://developers.cloudflare.com/kv/concepts/how-kv-works/), [R2 setup](https://developers.cloudflare.com/r2/get-started/), [R2 pricing](https://developers.cloudflare.com/r2/pricing/)
- **Firebase Spark.** It can supply sign-in and a database, but Cloud Storage for Firebase requires the pay-as-you-go Blaze plan. Screenshot uploads would need another service. [Firebase billing](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans), [Firebase Storage requirements](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024)
